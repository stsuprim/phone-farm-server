# Mac mini steps for the 2026-11-21 update (long runs)

For Rinor: paste everything below the line into Claude Code on the Mac mini, started inside the project folder
(`phone-farm-server`). About ten minutes; one step needs a laptop or phone with Lotus open on the Phones page.

---

You are updating the "Phone Farm Server" on this Mac mini for long runs: stream sockets with a heartbeat, WebRTC links
that can't connect given up, a server that survives a forgotten promise rejection, one shutdown with a deadline,
`server.log` rotated, and launchd limits. Read the `README.md` section "Long runs (2026-11-21)" first. **Never print,
log or paste `.env` or the API token**; use it only through shell variables, as below. Don't `git push`, and don't edit
the source (the auto-updater would undo it): report anything wrong.

```sh
cd ~/phone-farm-server   # or wherever the project is (the plist's WorkingDirectory)
set -a; . ./.env; set +a
B="http://localhost:${PORT:-8787}"; H="Authorization: Bearer $API_TOKEN"
P=~/Library/LaunchAgents/com.lotus.phonefarm.plist
```

1. **Get the new code.** The auto-updater pulls GitHub main within about a minute of the push. Confirm
   `ls src/lifecycle.ts docs/MAC_STEPS_2026-11-21.md` lists both. If not: `curl -s -X POST -H "$H" $B/update/now`,
   wait 60 s, check again. Then `curl -s $B/health` shows `uptimeS` and `rssMb` (no token needed).

2. **Add the new launchd keys to the installed plist** (it has your own paths, so don't copy the repo's over it; each
   `Add` that says "Entry Already Exists" is fine):

   ```sh
   cp "$P" "$P.bak-2026-11-21"
   /usr/libexec/PlistBuddy -c "Add :ThrottleInterval integer 10" "$P"
   /usr/libexec/PlistBuddy -c "Add :ExitTimeOut integer 30" "$P"
   /usr/libexec/PlistBuddy -c "Add :SoftResourceLimits dict" -c "Add :SoftResourceLimits:NumberOfFiles integer 8192" "$P"
   /usr/libexec/PlistBuddy -c "Add :HardResourceLimits dict" -c "Add :HardResourceLimits:NumberOfFiles integer 8192" "$P"
   plutil -lint "$P"
   ```

3. **Reload the service** (needed for the plist's keys; a kickstart doesn't read them):

   ```sh
   launchctl bootout gui/$(id -u)/com.lotus.phonefarm 2>/dev/null; sleep 3
   launchctl bootstrap gui/$(id -u) "$P"
   sleep 30; launchctl print gui/$(id -u)/com.lotus.phonefarm | grep -E 'state|pid|exit timeout'
   launchctl print gui/$(id -u)/com.lotus.phonefarm | grep -iA3 'resource limits\|NumberOfFiles'
   curl -s $B/health
   ```

   Expect `state = running`, `exit timeout = 30`, the 8192 open-files limit in the job's description (if `print`
   doesn't show it, `/usr/libexec/PlistBuddy -c "Print" "$P" | grep -A2 ResourceLimits` must), and `/health` with a
   small `uptimeS`.

4. **The log's rotation.** `ls -la server.log*`. If `server.log` was over 20 MB before this update, there is now a
   `server.log.1` and `server.log` started again small; `tail -n 20 server.log` still shows new lines (launchd writes on
   after the cut). If it was smaller, nothing changed: that's right.

5. **A viewer that sleeps** (needs Lotus): open a phone's live view in Lotus on a laptop, then close the laptop's lid
   (or turn its Wi-Fi off) for a minute. Within about 20 s `grep -E "rtc|stream .* dead link|control .* dead link" server.log | tail`
   shows the link ended (`stayed disconnected`, `did not connect`, or `nothing heard ... closing the dead link`), and
   `curl -s -H "$H" $B/phones | python3 -c 'import sys,json; [print(p["name"], p["capturing"], p["stats"]["viewers"], p["stats"]["controlLink"]["open"]) for p in json.load(sys.stdin)]'`
   shows that phone with `False 0 0` a little later (no capture, no viewer, no open link). Open the laptop again:
   Lotus's view comes back by itself.

6. **Leave it running** and note `curl -s $B/health` once a day for a few days: `rssMb` should stay about level (a
   steady climb means a leak: send the numbers). `ls -la server.log*` should never pass about 80 MB in total.
